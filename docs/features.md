## Features

- **AI-based routing** — a cheap classifier model (`OPENAI_MODEL_ROUTER`) categorises each request (via strict structured-output JSON, so it can't return an invalid category) and picks the tier; a keyword heuristic takes over if the classifier is unavailable, so `auto` mode never blocks on the router. A free pre-gate skips the classifier entirely for obvious prompts (a bare greeting → fast, a fenced code block → smart) so they answer instantly — each shortcut stands down only when the ONE category it would preempt (`casual_chat` for greetings; `coding`/`debugging` for a fenced code block) has its own override configured, not when some unrelated category does (`ROUTER_PREFILTER=false` to disable the pre-gate entirely).
- **Task-based model selection** — set `MODEL_<CATEGORY>` (e.g. `MODEL_CODING=claude-sonnet-5`, `MODEL_MATH=gemini/gemini-flash-latest`) and `auto` mode sends each task category to the model you've named best for it, across any provider. Unset categories fall back to the fast/smart tier; the tier still sets the token budget and reasoning effort.
- **Optional budget tier** — set `OPENAI_MODEL_BUDGET` (e.g. a cheap open-weight model via Groq/Together) and `auto` sends low-complexity fast-category tasks and bare greetings to it instead of the fast tier — with a tight token budget and minimal reasoning — so the cheapest slice of traffic gets the cheapest model. Opt-in (unset = routing unchanged); also selectable per request (`mode: "budget"`) or as a conversation pin, and it stretches the `DAILY_BUDGET_USD` cap further.
- **Zero-cost local models via Ollama** — point any tier at `ollama/<model>` (e.g. `OPENAI_MODEL_BUDGET=ollama/llama3.1:8b` with [Ollama](https://ollama.com) running locally; the `ollama_chat/` prefix works too) and that slice of traffic costs literally nothing: no API key, answers report `cost_usd: 0` (not "unpriced"), and free calls neither consume the `DAILY_BUDGET_USD` cap nor are ever blocked by it. If the local server turns out to be down, the normal paid fallback chain takes over — with each fallback candidate budget-gated individually, so a dead free primary can't route paid spend past an exhausted cap. Two deliberate exclusions: Ollama's `*-cloud` tags (proxied by the local daemon to Ollama's usage-metered paid cloud) are **not** auto-priced at $0 and stay "unpriced" unless you add a `MODEL_PRICING` entry; and an explicit `MODEL_PRICING` entry for any `ollama/` model always wins over the $0 default, for anyone accounting for local compute. Auth-style failures point at the local server ("is it running?") rather than a nonexistent API key. LiteLLM talks to `http://localhost:11434` by default; set `OLLAMA_API_BASE` for a non-default host.
- **Optional web search retrieval** — set `WEB_SEARCH=true` and `auto` mode grounds freshness-sensitive questions (news, prices, scores, weather, "latest"/"current" real-world events) in live results via each provider's own hosted search tool: OpenAI's Responses API `web_search` tool, or Anthropic's Messages API `web_search_20250305` tool — whichever provider the resolved model is served by, no new key either way (bills through the existing `OPENAI_API_KEY`/`ANTHROPIC_API_KEY`). The classifier decides per-question (never fires for "the current file"/"the latest commit" — only real-world freshness), only ever engages for an OpenAI- or Anthropic-served model (a Gemini/Bedrock/Mistral/other LiteLLM-routed model has no hosted search tool wired up here), and returns citations as a `sources` field on the answer regardless of which provider answered. A web-searched answer is never written to the response cache, so it can't go stale on replay.
- **Optional actions/webhooks (propose-then-confirm)** — set `ACTIONS_WEBHOOK_URL` (a Zapier "Catch Hook", Make "Webhooks" trigger, or any endpoint you control) and the model can *propose* a real-world action (send an email, add a row to a sheet, post a message) via a `pending_action` on the answer. Nothing ever fires automatically: the proposal is only executed after an explicit `POST /v1/conversations/{id}/messages/{id}/action {"confirm": true}` from the client, which then POSTs the model's payload to your webhook — the destination is never chosen by the model or caller, only from a fixed set the operator configured ahead of time. **Named routes**: set `ACTIONS_WEBHOOKS` (a JSON map, `{"send_email": "https://hooks...", "update_sheet": "https://hooks..."}`) to send different action *types* to different automations instead of one undifferentiated webhook — a real Zapier/Make integration, where each action gets its own Zap/scenario, not everything landing on one hook the receiving side has to branch on itself. When any named routes are configured, the model is restricted to proposing only those action types (an enum, not freeform text) — it can't invent an action name with nowhere real to go. `ACTIONS_WEBHOOK_URL` still works as the catch-all fallback for any action `ACTIONS_WEBHOOKS` doesn't name, or as the only route at all if that's the whole setup — fully backward compatible. The webhook body carries `{"action": str, "payload": object}`, not just the bare payload, so the receiving automation can tell action types apart even when they do share one destination. Engages for a resolved OpenAI- or Anthropic-served model — OpenAI's Responses API `function` tool and Anthropic's Messages API custom tool-use, same JSON schema either way, only the wrapper differs; a Gemini/Bedrock/Mistral/other LiteLLM-routed model has no tool-use path wired up here. Claude's tool call carries no answer text of its own, so the confirmation note ("I've prepared an action for your review...") is composed in for Claude the same way it already is for a text-plus-tool-call OpenAI response. A message with a pending action is never written to the response cache.
- **Optional moderation safety net** — set `MODERATION=true` and every incoming question is checked against OpenAI's moderation endpoint (`MODERATION_MODEL`, default `omni-moderation-latest`) before any budget reservation or model call. This is the one safety layer independent of the answering model's own judgment: routing/answering never second-guesses what a model decides to say, this checks what the user sent in the first place. A flagged question is refused immediately — empty answer, the flagged category names in `notes`, no model call, no budget spent, no response-cache write. Checked on the raw new turn (not a full conversation-context prompt), same reasoning `auto` mode's classifier uses `route_question` for. OpenAI-only (it's the one provider whose SDK exposes a dedicated moderation endpoint), no new key (bills through `OPENAI_API_KEY`), and — per OpenAI's own pricing — no extra token cost. A moderation-API outage fails open (the request proceeds unchecked, logged) rather than blocking the whole app. Off by default, like every other cost/behavior-affecting toggle here.
- **Optional image generation (OpenAI or Gemini/Imagen)** — set `IMAGE_GENERATION=true` and the model can generate images (e.g. "draw me a cat wearing a hat"). Two interchangeable backends picked by `IMAGE_GENERATION_MODEL`'s prefix, the same convention used for every other model setting in this app: the default `gpt-image-1` uses OpenAI's hosted `image_generation` tool (no new key, bills through `OPENAI_API_KEY`, the model itself decides when to call it); pointing it at `gemini/imagen-...` routes through LiteLLM and your existing `GEMINI_API_KEY` instead, triggered by a phrase heuristic since Gemini has no equivalent tool. Images come back as `images: ["data:image/png;base64,..."]` on the answer and persist with the message. Quality/size are configurable (`IMAGE_GENERATION_QUALITY`, default `high`; `IMAGE_GENERATION_SIZE`); a message with generated images is never written to the response cache.
- **Optional code execution** — set `CODE_EXECUTION=true` and the model can run Python in a hosted sandbox to verify a calculation or test a snippet instead of reasoning its way to an answer it can't check — same trust boundary as web search/image generation: it runs in the provider's own container, never on this machine. Reaches both an OpenAI-served model (the `code_interpreter` tool, bills through `OPENAI_API_KEY`) and a Claude-served one (Anthropic's beta `code_execution` tool, bills through `ANTHROPIC_API_KEY` — reached via the SDK's `client.beta.messages` namespace with an explicit beta opt-in header, since it isn't GA yet); the model decides for itself when running code would help, same as web search/actions. Each call comes back as a `code_results: [{"code", "logs", "images"}]` entry on the answer (the code, its stdout+stderr, and any plot images, as ready-to-render `data:image/...;base64,...` URLs) and persists with the message; a rough flat cost per call is added to the total (`CODE_EXECUTION_COST_USD`, default $0.03 — override for exact figures). Claude's generated files arrive only as a file-id reference, unlike OpenAI's inline base64 data, so each one is downloaded via a separate Anthropic Files API round trip (metadata, to check it's actually an image, then content) before landing in `images`; a non-image generated file (a CSV, a saved dataset, ...) or a failed download is silently skipped rather than surfaced, since nothing in the UI renders anything but an image there. A message with executed code is never written to the response cache. Each code block in the UI is collapsible and has its own 📋 copy button, the same one used for regular markdown code fences.
- **Image input / vision** — attach up to 4 images to a question (the 📎 button in the UI, pasting a screenshot directly into the question box from your clipboard, dragging a file onto the composer, or `images: [...]` on the request as `data:image/{png,jpeg,gif,webp};base64,...` URLs) and the resolved model sees them alongside the text — no opt-in flag, no new key, works across **every** provider (OpenAI, Anthropic/Claude, and any LiteLLM-routed model whose provider supports vision). Paste and drag-and-drop both go through the exact same validation/preview path as the 📎 picker (same 4-image cap, same skip-status messaging, and — since the drop target also accepts documents — the same PDF/plain-text handling as Document input below); the composer highlights while something's dragged over it. A copied screenshot has no text representation, so pasting one never interferes with a normal text paste. Attached images persist with the user's message and are reused automatically on regenerate. A request with attached images is never served from or written to the response cache.
- **Automatic image cost reduction** — two automatic, no-opt-in transforms (`IMAGE_DOWNSCALE`, `OCR_REPLACEMENT`, both **on by default**) run on attached images right before they reach the model, never touching what's persisted: large images are resized down to a bounded resolution (`IMAGE_DOWNSCALE_MAX_DIMENSION`, default 1024px), and images that are mostly text get run through a local Tesseract OCR pass, sending the extracted text instead of the image entirely when it's confident and dense enough — both far cheaper than full-resolution image tokens for the same content. Both fail safe (any decode/library error just sends the original image unchanged) and are skipped entirely whenever the question implies fine detail matters ("read the small text", "zoom in", "exact wording", ...). Substitutions are recorded in the answer's `notes` rather than happening silently, and both flags are editable at runtime from the Settings panel like any other feature flag.
- **Optional concise-answer mode** — set `CONCISE_MODE=true` and a brevity instruction ("no preamble, no filler or hedging, prefer bullet points/short paragraphs over prose") is appended to every outgoing prompt. Output tokens typically bill 3–10x the input rate, so trimming answer length is usually the single biggest lever on a call's actual cost, distinct from every other lever here (which all target input/context size instead). Unlike `IMAGE_DOWNSCALE`/`OCR_REPLACEMENT`, this defaults **off**: it changes what the model actually says, not just what it's billed for, so it needs an explicit opt-in rather than being silently on. Threaded so it reaches the model whichever provider is resolved — folded into the outgoing prompt directly for OpenAI/LiteLLM, and into the native `system` param for an Anthropic call using the prompt-caching split (see Provider prompt caching above), since that call never sends the plain prompt text at all.
- **Document input** — attach up to 4 PDF or plain-text documents to a question (the same 📎 button, dragging a file onto the composer, or `files: [{"filename", "data"}]` on the request) and the resolved model reads them alongside the text — same no-opt-in, every-provider design as vision, each translated into that API's own document/file content block (OpenAI's `input_file`, Anthropic's `document` block, LiteLLM's `file` block). Attached files persist with the user's message and are reused automatically on regenerate. A request with attached files is never served from or written to the response cache.
- **Voice input** — click the **$ 🎤** button to record a question instead of typing it; the clip is transcribed via `POST /v1/transcribe` (OpenAI's transcription API, `TRANSCRIPTION_MODEL`, default `gpt-4o-mini-transcribe`) and the text is inserted into the question box for you to review and send. A discrete, explicitly user-triggered action rather than something threaded through the routing/fallback machinery — a failure returns a real HTTP error, not a 200 with an empty answer. Right next to it, a **🗣️ Free voice input** button offers the same composer-filling behavior using the browser's own `SpeechRecognition` API — zero API cost, entirely on-device, but lower accuracy and Chrome/Safari only (no Firefox implementation exists to fall back to).
- **Voice output** — click the **$ 🔊** button on any assistant message to hear it read aloud, via `POST /v1/speak` (OpenAI's TTS API, `SPEECH_MODEL`/`SPEECH_VOICE`, defaults `gpt-4o-mini-tts`/`alloy`); click again (now ⏹) to stop. Same discrete, user-triggered design as voice input — a real HTTP error on failure, no routing/fallback story to it. Right next to it, a **🗣️ Free text-to-speech** button reads the same message using the browser's own `SpeechSynthesis` API — zero API cost, entirely on-device, lower voice quality. Starting either one stops whichever (paid or free) was already playing.
- **Runtime-editable model map** — a **Settings** panel (and the `/v1/settings` API) lets you re-point any tier or task category to a different model live, without restarting: a saved value overrides the matching env var, and clearing it reverts to the env/default. The panel shows each category's effective model, where it came from (override / env / default), and warns when a chosen model's credential isn't set. Global map; set `ALLOW_SETTINGS_WRITE=false` to make it read-only on shared deployments. A **Search settings** box filters all three sections (tiers, task categories, optional features) by label or key as you type — client-side, hiding whole sections once they have no matches — since between the 6 tiers and 11 task categories the panel gets long. The same panel's **Optional features** section covers the cost-affecting tool flags (`WEB_SEARCH`, `IMAGE_GENERATION`, `CODE_EXECUTION`) as live checkboxes — the same override > env > default chain as a model tier, so turning one off mid-session needs no `.env` edit or restart. **⬇️ Export config**/**⬆️ Import config** back up and restore just the overrides (not env vars or defaults) as one JSON file — client-side, looping the existing single-key `PUT`/`GET` endpoints like the conversation bulk actions, so one bad key on import doesn't block the rest ("Imported 2 of 3 overrides (1 failed)."). Export stays available even when the server is read-only; import is disabled along with every other edit in that case.
- **OpenAI-compatible `/v1/chat/completions`** — point any tool built against the OpenAI SDK/wire format (LangChain, an IDE plugin, a script that already talks to OpenAI) at this app instead, and it inherits routing/caching/budget behavior for free: just repoint `base_url`. `model` doubles as this app's routing mode (`auto`/`budget`/`fast`/`smart`) or forces an exact model, same convention as a conversation's model pin; supports both plain and streaming (`stream: true`, standard `chat.completion.chunk` SSE frames) responses. Stateless, same as `/v1/ask` — nothing is persisted, the caller resends the full `messages` history every call.
- **Multi-provider** — any tier (`OPENAI_MODEL_FAST` / `_SMART` / `_FALLBACK`) can point at an OpenAI model, a Claude model (any name starting with `claude`), or any **LiteLLM** provider-prefixed model (`gemini/…`, `bedrock/…`, `mistral/…`, `groq/…`, and 100+ others). OpenAI goes through the native Responses API and Anthropic through the native Messages API; everything else is dispatched through LiteLLM. Set that provider's standard credential (`GEMINI_API_KEY`, `MISTRAL_API_KEY`, AWS creds for Bedrock, …). The `auto` router itself stays on OpenAI.
- **Cross-vendor fallback chain** — if the primary model call fails, the orchestrator retries through `OPENAI_MODEL_FALLBACK`, then `OPENAI_MODEL_FAST`, then `OPENAI_MODEL` (duplicates and the failed model removed), tagging the result `->fallback`. Candidates on a **different provider** are tried first, so pointing `OPENAI_MODEL_FALLBACK` at e.g. `claude-sonnet-5` survives a whole-provider OpenAI outage. Rate-limit / quota (429) errors fail over too, but **only cross-provider** — the same throttled key would just be rejected again.
- **SSE streaming** — answers stream incrementally over `text/event-stream` with a strict `meta` / `delta` / `done` / `error` event contract.
- **Conversation persistence + auto-titling** — conversations and messages live in SQLite; the first question of a generically-titled conversation becomes its title (trimmed to 70 chars).
- **Long-conversation memory** — the recent turns (12–24 of them; see Provider prompt caching below for why it's a range, not a fixed 12) are sent verbatim and everything older is folded into a compact summary (one cheap `OPENAI_MODEL_ROUTER` call), so long threads keep their whole context instead of forgetting anything past the window. The summary is cached per conversation and only the newly-aged-out turns are folded into it each time — so the summarizer call stays cheap as a thread grows, instead of re-summarizing the whole older history from scratch on every single answer. Short threads (≤ 12 prior messages) are untouched and make no extra call; turn it off with `SUMMARIZE_HISTORY=false`.
- **Optional cross-conversation memory** — set `CROSS_CONVERSATION_MEMORY=true` and a new turn on any conversation can recall relevant exchanges from your OTHER conversations too, via embedding similarity (OpenAI's embeddings API — no new key, bills through `OPENAI_API_KEY`), and folds up to `MEMORY_TOP_K` (default 3) of them into the prompt as extra context — the same "no vector DB, brute-force cosine scan" design as Semantic caching below, storing an embedding of just the QUESTION alongside the answer as plain text. This is a genuinely different mechanism from long-conversation memory above: that folds a summary of THIS conversation's own older turns; this reaches across conversation boundaries, and is most valuable on a brand-new conversation that has nothing else to draw on yet. Deliberately a softer guarantee than Semantic caching's exact-answer reuse — a false positive here just adds a possibly-irrelevant snippet the model is told to use its own judgment on ("may or may not actually be relevant"), not a wrong answer served outright, so the match threshold (`MEMORY_THRESHOLD`, default 0.75) is much looser than that module's 0.96. Scoped to the main ask/ask-stream endpoints only (not regenerate/edit, not the stateless `/v1/ask`) and always excludes the asking conversation's own past entries (already covered by its own summary). Entries are capped per owner (`MEMORY_MAX_ENTRIES`, default 500, oldest evicted first) so recall stays a fast scan even as history grows. Off by default; `GET`/`DELETE /v1/memory` report status and clear it (no dedicated UI, same as Semantic caching).
- **Provider prompt caching** (Anthropic) — distinct from the app's own response cache and from the history summarization above: this is the *provider* billing repeated tokens at a discount, not the app skipping a model call. The system-prompt/history-summary prefix only advances its "checkpoint" once the verbatim recent-turns window grows past 24 messages (folding it back down to 12) rather than shifting by one every single turn — so that prefix stays byte-identical across most consecutive turns instead of changing every call, which is what actually lets a provider's native caching hit. For an Anthropic-served model, that stable prefix is sent via the Messages API's `system` param with a `cache_control: {"type": "ephemeral"}` breakpoint, and the (much shorter) recent-turns-plus-question remainder is sent as the user turn — never both, since sending the same text in each would bill it twice instead of caching it. OpenAI gets the same stable-prefix benefit for free, with no extra plumbing: its Responses API caches automatically off the same now-stable, byte-identical prefix. LiteLLM-routed providers (Gemini, Bedrock, Mistral, Groq, Ollama) get the stability improvement (fewer wasted summarizer calls) but no explicit cache_control, since none of them support Anthropic-style cache breakpoints through this app's LiteLLM path. Anthropic's actual cache economics are read back from the API response, not just assumed: `cache_read_input_tokens` (served from a prior write, discounted) and `cache_creation_input_tokens` (written this call, at a premium — see Cost & token tracking below) are both captured and priced correctly, so `cost_usd` reflects what a cache-touching call really billed rather than silently omitting those tokens.
- **Optional auth + per-user data** — a static bearer token (`API_AUTH_TOKEN`) and/or username/password accounts with JWTs (`JWT_SECRET` + `/v1/auth/register` & `/v1/auth/login`, with a login/logout UI); either credential grants access, and both are off by default for a zero-friction local setup. When a user is logged in via JWT, their conversations are private to them; with auth off (or a static token) conversations live in a shared bucket, so existing setups are unchanged. JWTs carry a `jti` + a per-user session epoch, so `/v1/auth/logout` **revokes every one of a user's tokens at once** (losing both API access and conversation ownership at one chokepoint), and `/v1/auth/refresh` issues a fresh token while rotating out (revoking) the old one. Every authenticated request in the UI goes through one `authFetch` wrapper, which tells apart the two different reasons an action can 401 and messages each accordingly instead of every action surfacing its own generic "Failed to X": a token that used to work getting rejected (expired, or revoked from another tab) signs out locally and shows "Session expired — please sign in again."; there never having been a token at all (auth is required but nobody's logged in yet — the sign-in form lives in the sidebar footer, easy to miss since the main chat UI stays fully visible either way) shows "Log in to do this" instead, with no sign-out needed since there was no session to lose. A persistent banner at the top of the chat panel makes that second case discoverable up front rather than only after a failed action — "🔒 Sign in required" with a **Sign in** button that focuses the sidebar's username field — shown only when JWT is enabled and nobody's logged in, and gone the moment they are. The static-token deployment mode gets the same treatment, worded for what it actually has: "🔒 API token required" (no sign-in form to point at, just the token field) when a static token is configured and none has been entered yet, and a rejected token says so explicitly ("Your API token was rejected...") instead of the JWT-flavored "session expired" message that wouldn't make sense here. The sidebar's token field itself drops its misleading "(optional)" label whenever a token is actually required.
- **Optional rate limiting** — set `RATE_LIMIT` (e.g. `60/minute`) to throttle the ask endpoints per client IP; unset leaves them unthrottled. The auth endpoints (`register`/`login`/`logout`/`refresh`) have their own limiter that's **always on** regardless of `RATE_LIMIT` (`AUTH_RATE_LIMIT`, default `5/minute`) — closing off brute-force/registration-spam by default rather than requiring opt-in. When the ask/regenerate/edit endpoints do throttle a request (429), the UI shows a clear "You're sending requests too fast" status instead of a bare "Request failed (429)", and restores the question text so nothing typed is lost.
- **Per-tier budgets** — separate max-output-token limits and reasoning-effort levels for the fast and smart tiers, so quick answers stay quick and hard problems get room to think.
- **Cost & token tracking** — every answer reports input/output tokens and an estimated USD cost (per built-in, overridable price list), shown per message and as a running per-conversation total in the UI — so the savings from routing cheap tasks to cheap models are visible. Provider prompt-cache economics are priced as three separate tiers, not folded into a flat input rate: tokens served from the provider's cache are billed at a discount (`CACHED_INPUT_MULTIPLIER`, default 0.1x input), tokens newly *written* to a provider's cache (Anthropic's `cache_creation_input_tokens` — see Provider prompt caching above) are billed at a **premium**, not a discount (`CACHE_WRITE_MULTIPLIER`, default 1.25x input, since establishing a cache entry costs the provider extra work), and everything else at the plain input rate. Getting the write side wrong in either direction would silently mis-price every Anthropic call that touches the cache — either overstating cost (billing a cache write as if it were a discount) or understating it (not billing the premium at all).
- **Daily spend cap** — set `DAILY_BUDGET_USD` and, once the next call's worst-case cost would push today's total (across all users, per UTC day) past the limit, the call is refused before any model runs. The check reserves that worst-case cost atomically as part of the same check (not a separate later write), so multiple concurrent calls can't each pass the same stale total and jointly overshoot the cap; the reservation is reconciled down to the call's real cost once it completes, or released if it never dispatched. Every billable call is counted in a durable spend log — including empty/truncated reasoning calls that aren't saved as messages, and `/v1/speak`/`/v1/transcribe` (priced by a flat/per-character estimate, since neither bills per LLM token). `/v1/status` reports only whether a cap is active; the live figures stay off the public endpoint.
- **Per-owner daily spend cap** — set `DAILY_BUDGET_PER_OWNER_USD` for the same kill-switch scoped to one caller's own spend (see `spend_log`'s `owner` column) instead of everyone's combined total, so one user maxing out their own budget doesn't starve everyone else's, and vice versa. Independent of `DAILY_BUDGET_USD`: either, both, or neither can be set, and both are checked atomically in the same reservation when both are configured — whichever is hit first refuses the call. Applies to the shared/unowned bucket too (static-token or no-auth deployments), where it's simply redundant with the global cap unless set tighter than it.
- **Response caching** — an identical prompt (same mode + model config) returns instantly and for free, with no model call — not even the classifier. The cache key folds in a signature of the model map, so editing a tier/category or a routing env var auto-invalidates stale entries; TTL and max-entry eviction are configurable, cached answers are badged in the UI, and `no_cache` on a request forces a fresh answer.
- **Optional semantic (paraphrase) caching** — set `SEMANTIC_CACHE=true` and a paraphrased repeat of a **context-free** question (e.g. "what's the capital of France?" vs "capital of france?") gets served from cache too, matched via OpenAI embedding similarity instead of exact text — no new key, bills through `OPENAI_API_KEY` (embeddings are negligible cost, priced like the router classifier/summarizer). Deliberately narrower than the exact cache because the failure mode is worse: a wrong exact-match hit can't happen by construction, but a wrong semantic hit means serving a plausible-but-different answer for a merely-similar-sounding question. Two guardrails keep that risk in check — it's **only ever applied to a context-free question** (no conversation history or custom system prompt behind it, since two similar-looking context-BEARING prompts can still imply different answers), and it's **off by default** with a conservative similarity threshold (`SEMANTIC_CACHE_THRESHOLD`, default `0.96`). No vector DB dependency: embeddings are brute-force cosine-matched in Python, kept fast by a deliberately small entry cap (`SEMANTIC_CACHE_MAX_ENTRIES`, default 200). A semantic hit is clearly marked in the answer's `notes` (with its similarity score) rather than looking identical to an exact hit, and records the same avoided-cost tracking as an exact-cache hit. Manage it via `GET`/`DELETE /v1/semantic-cache` (status/clear, mirroring `/v1/cache`), and toggle it at runtime from the Settings panel like any other feature flag.
- **Optional self-updating model catalog** — set `MODEL_CATALOG_SYNC=true` and this app pulls [LiteLLM's published pricing feed](https://github.com/BerriAI/litellm) to keep model prices current, instead of relying solely on the hand-maintained defaults in `app/usage.py`. Pricing precedence, lowest to highest: the synced catalog → the hand-bundled defaults (deliberately curated for this app's own tier examples, so they never go stale even before a first sync) → your own `MODEL_PRICING` (always wins over both). This is the **only thing in this app that ever calls a server other than a configured LLM provider** — every other network call goes to an API you deliberately pointed the app at — so it's opt-in, unlike everything else here that only affects a cost *estimate*. No background scheduler: a sync only happens when you click **🔄 Sync now** in Settings, or lazily (at most once per `MODEL_CATALOG_SYNC_INTERVAL_HOURS`, default 24h) the next time you open the Settings panel while enabled — opening Settings is what "on a schedule" means here. A failed sync (network error, bad response) leaves the last-known-good catalog untouched and surfaces the failure rather than silently going stale or wiping good data. After each sync, model names that weren't present in the *previous* sync are surfaced as a **🆕 N new models** notice (empty on the very first sync, since there's nothing yet to diff against). Manage it via `GET`/`POST /v1/model-catalog{,/sync}`.
- **Regenerate / switch-model** — re-run a conversation's last answer (always fresh, bypassing the cache), optionally forcing a specific model or tier instead of the routed one. The old answer is replaced in place. A forced model bypasses the classifier and the cache entirely.
- **Truncation detection + Continue** — when a provider stops an answer early because it hit `max_output_tokens` (OpenAI's `status: "incomplete"`, Anthropic's `stop_reason: "max_tokens"`, or a LiteLLM provider's `finish_reason: "length"`), the UI shows a "⚠️ Response was cut off" notice with a **Continue** button instead of silently showing a truncated answer. Continue (`POST /v1/conversations/{id}/messages/{message_id}/continue`) asks the model to resume exactly where it left off and appends the result to the same message — tokens/cost accumulate across every continuation, so the total reflects everything spent producing the full answer. Non-streaming by design: a continuation is an occasional follow-up action, not the primary answering path, so a second streaming implementation wasn't worth the added surface.
- **Ambiguity-triggered clarifying questions** — the router's classifier call (already made once per `auto` request to pick a tier) also checks whether the new message references something ambiguous in the last few turns (e.g. "this"/"it" could mean either of two things just discussed). When it does, the orchestrator returns a clarifying question directly instead of guessing and calling a fast/smart model — no new LLM call, and cheaper than the alternative of burning a full answer on the wrong interpretation. Auto mode only; explicit fast/smart/budget modes skip the classifier entirely, same as today.
- **Edit a past message** — click ✏️ on any user message to edit its text and resend it; everything from that turn onward (the old answer, and any later turns) is discarded and a fresh answer is generated from that point. Attachments (images/files) on the edited turn carry over unchanged — only the text is editable. A failed or aborted edit leaves the original message and its answer untouched, the same "replace only on success" safety net as regenerate.
- **Draft auto-save** — an unsent question is saved per conversation (client-side, in `localStorage`) as you type, so switching conversations or reloading the page never silently discards it — and, just as important, never leaves it sitting in a different conversation's composer where it could get sent to the wrong thread. Cleared once the question is actually sent.
- **Delete a single message, with Undo** — click 🗑️ on any message to remove just that one message, whatever its role, without touching anything else in the conversation — distinct from regenerate (replaces the last answer) and edit (discards everything from a point onward and re-asks). Asks for confirmation first, then offers an 8-second "Undo" the same way deleting a whole conversation does. Restoring a single message can't reuse Import (that always builds a whole new conversation), so it goes through a dedicated `POST /v1/conversations/{id}/messages/restore` instead — recreates the message (fresh id, no model call) in its *existing* conversation from the client-side snapshot taken right before the delete, same fidelity as Import (attachments included).
- **Bookmark a message** — click 🏷️/🔖 on any message (either role) to mark just that one turn (`PUT /v1/conversations/{id}/messages/{message_id}/bookmark`), distinct from favoriting the whole conversation. A pure marker like favorite/archive — doesn't touch the conversation's `updated_at`, and persists across reloads.
- **Bookmarks panel** — the **Bookmarks** button in the chat header (`GET /v1/bookmarks`) lists every message you've bookmarked across *every* conversation, newest first, each with a snippet and its parent conversation's title — reviewing what you bookmarked no longer means hunting back through each conversation individually. Clicking a row jumps straight to that exact bookmarked message (see deep-linkable messages above), scrolling to and briefly highlighting it rather than just opening its conversation. A 🏷️ button on each row unbookmarks it right there (the same `PUT .../bookmark` toggle the message view uses) without needing to open that conversation first, offering a 5-second **Undo** afterward (re-bookmarks via the same toggle) in case that was a misclick. A **Search bookmarks** box filters the list client-side by conversation title or message content as you type. **⬇️ Export** downloads the currently-filtered list as one Markdown file (conversation title, timestamp, and full content per bookmark) — entirely client-side, built from what's already loaded, and disabled when there's nothing to export (no bookmarks at all, or none matching the current search). Owner-scoped like every other conversation-derived endpoint.
- **Saved prompt templates** — the **📝 Templates** button in the chat header opens a small panel of reusable prompt snippets (`GET/POST/PATCH/DELETE /v1/templates`), owner-scoped like conversations. Distinct from a single conversation's own Custom Instructions (which apply automatically, to just that one conversation): a template is a manually-inserted snippet you can reuse across *any* conversation's composer — a boilerplate question, a checklist, a standing set of constraints. Clicking a saved template inserts its content into the composer (appended after anything already typed) and closes the panel; ✏️ renames/edits one in place, 🗑️ deletes it. Name capped at 80 chars, content at 4,000.
- **Keyboard shortcuts** — `Ctrl+K` / `⌘K` jumps into the conversation search box from anywhere. `Alt+N` / `⌥N` starts a new conversation and focuses the composer, ready to type — `Ctrl+N`/`⌘N` is deliberately not used, since browsers reserve it for "new window" and page JavaScript can't intercept it. `Alt+B` / `⌥B` opens **Bookmarks** the same way (`Ctrl/Cmd+Shift+B` is reserved by Chrome/Firefox for the bookmarks bar toggle, so this avoids that combo too). `Escape` backs out of whatever's open, most-local first: the Instructions panel, an in-progress message edit, then an active search — it never interferes with the Settings/Usage modals, which already close on their own `Escape` handler. Press `?` (or click the ❓ button next to the theme toggle) for a help modal listing all of these — suppressed while typing in the composer or any other text field, so a literal "?" in a question never pops it open. With a conversation row focused in the sidebar, `↑`/`↓` move to the previous/next conversation and `Home`/`End` jump to the first/last, like a standard listbox — scoped to that one row's focus, not a global handler, so it never fires while typing or interacting elsewhere.
- **Light / dark theme toggle** — the 🖥️/☀️/🌙 button at the top of the sidebar cycles System → Light → Dark → System. System (the default, and the only behavior before this toggle existed) follows the OS's `prefers-color-scheme`; an explicit Light or Dark choice overrides it regardless of the OS setting, and persists in the browser's `localStorage` (client-side only — no account setting, no server round-trip).
- **Background reply notifications** — the 🔕/🔔 button next to the theme toggle opts into being told when an answer finishes while this tab isn't the one you're looking at: the tab title flashes to "💬 New reply" (reverting the moment you switch back), and, if you grant the browser's Notification permission, a native OS notification pops up too, click-to-focus straight into that conversation. Off by default, and only ever fires for the tab that's actually hidden — permission is requested once, right when you turn it on, never on page load unprompted. Once notifications are on, a second 🔈/🔊 toggle appears for an audible cue — a short beep synthesized on the spot via the Web Audio API, so there's no audio asset file or new dependency. Entirely client-side (`localStorage`), no new endpoint.
- **Export a conversation** — the ⬇️ Export control in the chat header downloads the current conversation as Markdown (human-readable, with sources linked and attachment counts noted) or JSON (the full raw message data, including attachment content), opens it as a print-ready **PDF (print)** document in a new tab and hands off to the browser's native print dialog, **📋 Copy as Markdown** puts the same Markdown straight on the clipboard — no file to save and reopen, just paste into Slack/a doc/an email — or **🔗 Copy link** puts this conversation's `?c=<id>` deep link on the clipboard instead, for sharing the live conversation itself rather than a static copy of it. All five are entirely client-side — no server round-trip, since the messages are already loaded in the UI.
- **Export all conversations** — the **⬇️ Export all** button in the sidebar backs up every conversation (including archived ones) as one JSON file: `{"exported_at", "conversations": [{"conversation", "messages"}, ...]}`, each entry in the same shape a single-conversation JSON export produces — so any one of them can be pulled out and re-imported individually via `POST /v1/conversations/import`. Fetches each conversation's messages client-side (one request per conversation); no dedicated backend endpoint.
- **Import a conversation** — the **⬆️ Import conversation** control in the sidebar re-creates a conversation from a JSON file previously produced by Export (`POST /v1/conversations/import`): a fresh conversation with new message ids, no model calls involved. Everything Duplicate also copies comes back too — the model pin, custom instructions, tags, and each message's tokens/cost/cached flag/sources/truncated flag/code_results/attachments (images/files) — full fidelity, restored through the exact same validators a freshly-attached upload goes through (count/size caps, `data:` URL/mime allowlist — see `AskRequest`), so a re-imported attachment gets no less scrutiny than a new one, and a malformed/oversized one fails the whole import (`422`) rather than silently getting dropped. It also accepts a whole **⬇️ Export all** bundle in one drop, restoring every conversation in it (best-effort: one bad entry doesn't abort the rest — the status line reports how many succeeded).
- **Duplicate a conversation** — the **Duplicate** button in the chat header (`POST /v1/conversations/{id}/duplicate`) copies the current conversation — title (suffixed " (copy)"), pin, custom instructions, and every message with full fidelity (attachments, cost, tokens, truncated flag, code_results) — into a brand-new one, so you can branch off and try a different approach without losing the original. A server-side DB-to-DB copy, unlike import, so attachments round-trip intact; any pending action is deliberately not carried over, since confirming it on the copy would re-fire the same webhook a second time.
- **Branch a conversation from a message** — the 🌿 button on any message (`POST /v1/conversations/{id}/messages/{message_id}/branch`) copies the conversation — title (suffixed " (branch)"), pin, and custom instructions — into a brand-new one, but truncated to only the messages up to and including that one, rather than the whole thing. For exploring "what if I'd asked differently from here" without losing the original conversation's continuation, and without the noise of copying every later message along with it. Favorite status is deliberately not carried over (same reasoning as archived on Duplicate: a branch implies a fresh working copy).
- **Summarize a conversation** — the **🧾 Summarize** button in the chat header (`POST /v1/conversations/{id}/summarize`) generates a short, on-demand TL;DR of the whole conversation — key topics discussed, decisions reached, open questions — using the same cheap router model the internal history-folding summarizer already calls, so it costs about as much as one ordinary reply. Distinct from that internal summarizer's terse, fact-dense notes (meant to feed back into the model as context, not for a human to read): this one is written for you. Ephemeral by design — nothing is persisted, so re-clicking regenerates a fresh one rather than serving a stale cached copy — with a **📋 Copy** button once it's in. Disabled for an empty conversation (`400`); a `502` surfaces if the model call itself fails.
- **Compare models** — the **Compare** panel (`POST /v1/compare`) asks the same question of 2–4 specific models side-by-side and reports each answer alongside its cost, tokens, and latency — a direct, standalone way to see what multi-provider routing is actually trading off, independent of any saved conversation. Pick from your configured tier models, or type any model name into the "Add a specific model" field (e.g. `groq/llama-3.3-70b-versatile`) — useful right after adding a new provider key. Dispatched one model at a time (not in parallel), so the daily-budget accounting across the batch stays correct; one model being unconfigured or failing never aborts the rest of the comparison, since it's reported as an empty answer + explanatory notes rather than an error. Once results are in, **📋 Copy as Markdown** puts the whole comparison (question, each model's answer, cost/tokens/latency) on the clipboard in one go, the same "no file to save and reopen" convenience conversation export already has. **💬 Continue in new conversation** on any one result bridges Compare back into the app proper — it saves that model's question/answer as a real, saved conversation pinned to that model (via the same `POST /v1/conversations/import` a JSON re-import uses, so no second model call is made) and switches straight to it, so liking one model's take on a question doesn't mean starting over from scratch to keep talking to it.
- **Copy to clipboard** — a 📋 button on every message copies its full text (via the browser's Clipboard API); fenced code blocks in assistant answers get their own **Copy** button so a snippet can be grabbed without the surrounding prose. Both flip to a brief "copied" confirmation on success; a failure (e.g. clipboard permission denied) surfaces a status message rather than failing silently.
- **Search conversations** — the sidebar search box (`GET /v1/search?q=...`) matches against both conversation titles and message content, so an old conversation is findable even if its auto-generated title doesn't mention what you're looking for. Debounced client-side; results show a matching snippet, with every occurrence of the search term highlighted in the title and snippet so you can see exactly what matched, and jump straight to that conversation on click. Owner-scoped like every other conversation endpoint — a search only ever surfaces your own conversations.
- **Sort the conversation list** — a **Sort** dropdown in the sidebar switches between the default **Recent** order (favorited conversations first, then most-recently-updated — exactly what the backend already returns) and **Name (A-Z)**, an alternate alphabetical view rather than an extra grouping layered on top. Purely client-side; combines with the tag and Favorites-only filters, which narrow the list before this re-orders it.
- **Back to previous conversation** — a **← Back to "..."** button appears in the sidebar once you've switched conversations at least once, taking you straight back to whichever one you were just in. Clicking it flips the two, Alt+Tab-style, so a second click returns you to where you started — no history stack, just the single last-selected id. Only shown while that conversation still exists (it disappears if it's since been deleted) and works even if the current tag/favorites filter would otherwise hide it from the visible list, since it's restoring a known conversation rather than browsing the filtered one.
- **Deep-linkable conversations and messages** — the selected conversation is reflected in the URL as `?c=<id>` (via `history.replaceState`, so switching conversations doesn't pile up browser history entries), so reloading the page, bookmarking it, or sharing the link lands back on the same conversation instead of always falling back to the default pick. Loading a `?c=` for a conversation that doesn't exist (deleted, wrong owner, or just made up) falls back to the normal default selection rather than erroring. Adding `&m=<messageId>` scrolls to and briefly flashes-highlights that one specific message once it loads, then strips itself from the URL — a 🔗 button on every message copies exactly this link to the clipboard, and clicking a row in the **Bookmarks** panel now jumps straight to the bookmarked message (not just its conversation) using the same mechanism.
- **Message-count badge** — each sidebar row shows a small badge with its message count (`GET /v1/conversations` now returns `message_count` via a correlated subquery, since `messages(conversation_id)` is already indexed). Hidden entirely for a conversation with no messages yet, rather than showing a "0" — a quick-glance signal for which conversations actually have content versus which were just created.
- **Onboarding hints for a fresh install** — with zero conversations and none selected, the main panel replaces the terse "Create or select a conversation" placeholder with a short welcome message and concrete first steps (create a conversation, ask a question, add provider API keys in Settings). Reverts to the plain placeholder as soon as at least one conversation exists, so it never talks down to a returning user.
- **Find in conversation** — the **🔎 Find** button in the chat header opens an inline find bar that searches just the open conversation's messages, cycling between matches (a match counter, ↑/↓ prev/next, Enter/Shift+Enter) and highlighting + scrolling to the active one. Distinct from sidebar search, which finds a *conversation* but doesn't scroll to or highlight anything inside it once it's open. Entirely client-side, no request — the messages are already loaded.
- **Jump to latest** — a floating button appears once you've scrolled away from the bottom of a long conversation, jumping straight back to the newest message on click. The whole page scrolls in this layout (nothing bounds the message list to the viewport), so this — and the existing "follow the tail while streaming" behavior — is measured off the page's own scroll position, not an inner pane; the button itself is fixed to the viewport for the same reason, or it would scroll out of view along with everything else.
- **Favorite conversations** — click the ☆/★ toggle next to any conversation in the sidebar (`PUT /v1/conversations/{id}/favorite`) to pin it to the top of the list, ahead of everything unfavorited; within each group, conversations still sort by most-recently-updated. A pure bookmark — starring doesn't touch `updated_at` or otherwise affect routing/caching. Carries over on Duplicate and Export/Import, the same field parity as the model pin and custom instructions. Check **★ Favorites only** in the sidebar to narrow the list down to just your starred conversations — a client-side filter, same as the tag filter, and combines with it (both narrow the same list at once).
- **Tag conversations** — the **Tags** button in the chat header (`PUT /v1/conversations/{id}/tags`) sets a comma-separated list of freeform labels on a conversation (trimmed, deduped, capped at 15 tags of 30 characters each), shown as chips in the sidebar. A **Filter conversations by tag** dropdown appears once any conversation has a tag, narrowing the sidebar list client-side. A pure organizational marker like favorite/archive — doesn't touch `updated_at` — and carries over on Duplicate/Import, the same field parity as the model pin/instructions/favorite.
- **Archive a conversation** — the **Archive** button in the chat header (`PUT /v1/conversations/{id}/archive`) hides a conversation from the default sidebar list without deleting it — a softer, reversible alternative to Delete. Check **Show archived** in the sidebar to see and select archived conversations (tagged "(archived)"); the button then reads **Unarchive** to restore one. Archiving doesn't touch `updated_at`, and the conversation itself stays fully reachable (messages, ask, etc.) while hidden — it's a visibility filter, not a lock. Unlike the model pin/instructions/favorite, archived status is deliberately NOT carried over by Duplicate or Import, since both produce a fresh working copy you'd want to actually see.
- **Delete a conversation, with Undo** — the **Delete** button in the chat header (after a confirmation prompt) permanently removes a conversation and its messages (`DELETE /v1/conversations/{id}`). Deleting is real and immediate — there's no soft-delete/trash table — but for the next 8 seconds a "Deleted "..." Undo" banner offers one click to bring it back, restored via the same `POST /v1/conversations/import` a JSON re-import uses (fresh id, full fidelity — title/pin/instructions/favorite/tags/messages/attachments) built from a snapshot taken client-side right before the delete fires. An emptied conversation (no messages) restores via a plain create instead, since Import requires at least one message. Purely a convenience for "oops, wrong conversation" — not a substitute for Export as an actual backup.
- **Bulk archive/delete/export/tag conversations** — the **Select** button in the sidebar turns every conversation row into a checkbox; pick as many as you like, then **Archive selected**, **Delete selected**, **Export selected**, or **Add tag** to act on just that batch instead of one conversation at a time (or all of them, via Export all). Archive/delete/tag are best-effort like Export all/bulk import: each conversation is acted on individually via the same single-item endpoints, so one failure never blocks the rest — the status line reports the split (e.g. "Archived 2 of 3 conversations (1 failed)."). Export selected produces the same Export-all-shaped JSON bundle, just scoped to the checked conversations. Add tag *merges* the new tag into each conversation's existing tags rather than replacing them, since the underlying endpoint sets tags wholesale. Bulk delete asks for one confirmation covering the whole batch, not one per conversation.
- **Usage dashboard** — the **Usage** panel in the chat header (`GET /v1/usage?days=`) reads back your own slice of the same `spend_log` ledger that backs the daily budget cap: today's total, a by-day bar chart, and a by-model breakdown (calls, tokens, cost) over a selectable 7/14/30/90-day window. Owner-scoped — you only ever see your own spend, never the deployment-wide total (that stays off the public `/v1/status`). When `DAILY_BUDGET_PER_OWNER_USD` is set, it also shows how much of *your own* cap is left today (e.g. "$0.65 left of your $1.00 daily cap"); with only `DAILY_BUDGET_USD` set, it shows that configured limit as context. Either way, only the configured limit(s) are exposed here — never the live global spend total, which stays private to the operator. The **⬇️ Export CSV** button downloads the currently-shown window's daily spend, tokens, by-model breakdown, and the efficiency figure below as one CSV file — entirely client-side, built from data already fetched for the panel, no extra request.
- **The efficiency KPI (tokens per $1)** — a headline stat in the Usage panel, right next to today's spend: total tokens processed divided by total spend over the selected window (e.g. "128,571 tokens per $1 · last 14 days"). Spend alone conflates "the app got cheaper" with "I used it less" — this ratio is the thing routing/caching/downscaling work is actually meant to move, and should trend *up* as those features do their job even while raw usage grows. Shows **"All free"** (with the raw token count) when the window has usage but zero spend — e.g. an Ollama-only window — rather than a division-by-zero or a misleading `0`, and a plain "No usage yet" message when the window is genuinely empty. Sourced from the same per-day `spend_log` aggregation as the bar chart (`by_day[].tokens` alongside `by_day[].cost_usd`), so it's never a second, inconsistent computation.
- **Low-budget warning** — once your own remaining room under `DAILY_BUDGET_PER_OWNER_USD` drops to 15% or less of the cap, a small warning banner appears above the composer (e.g. "⚠️ Only $0.10 left of your $1.00 daily budget today.") — checked on page load and again after every answer, so it stays current without opening the Usage panel. Silent when no per-owner cap is configured. Reuses the same `/v1/usage` endpoint and the same owner-scoped privacy boundary — it only ever surfaces the caller's own room, never the live global spend.
- **Cost-visibility pass** — every button that triggers a real model/API call is marked with a `$` (Ask, Regenerate, Continue, Compare, AI voice output, AI voice input), so it's never a surprise which clicks cost tokens/credits and which are free (Templates, Bookmarks, Duplicate, Branch, Archive, Tags, Export, Import, and so on all stay unmarked). A small **$** button next to **❓ Keyboard shortcuts** explains the convention in one tooltip. A persistent **💰 sidebar indicator** ("💰 $0.42 today", or "💰 $0.42 / $5.00 today" when `DAILY_BUDGET_PER_OWNER_USD` is set) shows your own running spend for the day — loaded once via `GET /v1/usage?days=1` on startup and refreshed after every completed Ask/Regenerate/Continue/Compare/Speak/Transcribe call, always re-querying the server's own ledger rather than summing client-side, so it can't drift.
- **Avoided-cost tracking** — when the app's own response cache serves an answer instead of calling a model, what that call *would have cost* (the cache entry's own original `cost_usd`) is durably logged to a separate `avoided_cost_log` table, not just mentioned in passing notes and then discarded. Deliberately a separate table from `spend_log`: the daily budget cap only ever sums real spend, so mixing in "cost that was never actually incurred" rows would corrupt that total. A **🛟 sidebar indicator** ("🛟 $0.05 saved today") appears next to the 💰 spend indicator whenever today's avoided cost is nonzero, reusing the same `GET /v1/usage?days=1` refresh cadence as the spend indicator.
- **Live cost preview** — as you type, a small line above the composer shows what the question would cost *before you send it* (e.g. "~4,016 tokens · up to $0.0100 on gemini/gemini-flash-latest"), debounced 400ms after the last keystroke (`POST /v1/estimate`). This is a genuinely free preview, not a second billable call: it prices the SAME worst-case estimate the `DAILY_BUDGET_USD` gate itself uses on dispatch (`budget.estimate_worst_case` — ~4 chars/token for input, the resolved tier's max-output-tokens budget for output), and routing never reaches the paid classifier even in `auto` mode (`decide_route(..., client=None)` falls through to the free keyword heuristic instead). Clears the moment the composer is emptied or the question is actually sent, so a stale estimate can never linger for the next question.
- **Per-conversation model pin** — pin a specific model (or the `budget`/`fast`/`smart` tier) to a conversation so every new question in it uses that model, bypassing the router. A pinned model routes like switch-model (no classifier, no cache); clear the pin to return to normal per-mode routing. The `budget` option only appears (in the mode selector, the pin selector, and the regenerate-with menu) once `OPENAI_MODEL_BUDGET` is configured server-side.
- **Per-conversation custom instructions** — the **Instructions** panel in the chat header (`PUT /v1/conversations/{id}/system_prompt`) lets you set a persona/style/rules block (e.g. "Always answer in French") that's prepended to every question asked in that conversation — including the very first one, and every regenerate/edit. Cleared with an empty value; a filled dot on the Instructions button shows when one is active, so its effect is never invisible. Capped at 4,000 characters.
- **Telemetry** — every request gets a UUID request id and elapsed-ms timing, surfaced in the response `notes` and in structured logs.
- **OpenTelemetry tracing** — set `OTEL_EXPORTER_OTLP_ENDPOINT` to export request spans (enriched with the routing decision) to any OTLP collector — SigNoz, Grafana Tempo, Jaeger, etc. Off by default, zero overhead when unset.
